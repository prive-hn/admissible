# Run: worker-pool, 2026-08-29

First end-to-end run of the gate against code a real generator wrote, rather
than against constructed samples. Corpora in `corpora/worker-pool.*.json`.

## Method

**Corrected 2026-08-30 after review; the original text contradicted itself and
described data that is not in the repository.** What is committed, and all that
this file may be read as reporting, is `corpora/worker-pool.{median,wrap,
normpath,quantiles}.json`: **48 samples**, 12 per target, ingested as 4 lines ×
k=3 and replayed through `run_target`.

Every context received an identical instruction. That is asserted, not
recorded: each corpus's `task_sha256` hashes the target *label*
(`spec:normpath`), not the instruction text, so it carries no evidence about
what any context was asked and was told not to run or check anything against the standard
library: the gate exists because generators emit unverified output, so measuring
verified output would defeat the purpose.

The original text claimed both "60 independent contexts — one sample per
context" and "12 contexts × 4", which cannot both hold. The corpora record only
`model: worker-pool` and carry no per-sample context id, so **the independence
of the k samples within a line is not established by the committed data.** The
agreement figures below should be read with that in mind.

## Result 1 — the gate does not refuse correct work

| target | sealed | V1 refuted | V2 discord | escapes |
| --- | ---: | ---: | ---: | ---: |
| `median` | 4 | 0 | 0 | 0 |
| `wrap` | 4 | 0 | 0 | 0 |
| `normpath` | 4 | 0 | 0 | 0 |
| `quantiles` | 4 | 0 | 0 | 0 |

16 of 16 lines sealed. **Zero false refusals**, and this is not trivial: the 12
`normpath` samples were **12 textually distinct implementations** — different
variable names, different control flow, one tracking the leading slashes as a
string rather than a count. A checker comparing source text would have refused
most of them. The gate compares behaviour, and sealed all twelve.

Independently confirmed: every one of the 48 matches its stdlib oracle on 3,000
generated inputs. So the seals are correct, not lucky.

## Result 2 — detection could not be tested here, and the reason matters

**Not one of the 48 committed samples was defective.** Distinct implementations
per target were 2 (`median`), 7 (`wrap`), 12 (`normpath`), 5 (`quantiles`) —
real variation in *form*, none in *behaviour*.

**A `splitext` trap was run and its samples were not retained.** The intended
observation — that the contexts reproduced the CPython algorithm including the
undisclosed leading-dot rule, which `.bashrc` splits to `(".bashrc", "")` — has
**no corpus in this repository**, so it is not reproducible and is recorded here
as an unverified note, not as a result. Nothing downstream should rest on it.

What the committed data does establish stands on its own: zero of 48 samples
across four targets was defective. The conclusion is not that the generator is
careful; it is that
**this class of target cannot measure a generator at all.** `eval/bench` builds
each target as a stdlib reference implementation checked against the stdlib
itself. Both halves are in any modern generator's training data, so it does not
solve the task — it recalls the answer, and the answer is the oracle. The
differential refuter then compares the oracle to itself.

## What this means for the bench

The ceiling is structural, not a matter of adding targets. Any function whose
oracle is a well-known library function will produce this result, and
`normpath` and `quantiles` — added precisely because they were harder — did no
better than `median`.

Two consequences:

1. The false-positive half of the gate is now measured on real generated code
   and is clean: 16/16 lines sealed, over 48 correct implementations spanning wide
   textual variation. The seal requires concordance across a line's k samples,
   so it inherits the unrecorded-independence limitation below; what does not is
   that all 48 match their stdlib oracle, which is checked per sample.
2. The detection half cannot be measured this way. It needs targets whose
   correct answer is *not* recallable — real historical defects
   (`eval/realdefects/`), or novel specifications with no public reference
   implementation.

## Limits

- One generator. This is not a capability-tier comparison; every context ran
  the same configuration, so the numbers say nothing about how generators
  differ.
- Sample independence is asserted, not recorded. The corpus schema has no
  per-sample context id, so nothing in the committed data distinguishes 48
  independent draws from 12 contexts asked four times each.
- 4 lines × k=3 per target is small.
- Contexts were told not to verify their work. That is deliberate — it isolates
  first-draft output, which is what the gate is for — but it means these
  numbers describe unverified generation, not a generator with tools.
- The scenario buckets are meaningless here and are reported as one `recorded`
  scenario; see the note in `corpus.py`.
